## Approved follow-on designs and deferred modules

| ID | Status | Finding | Disposition |
|---|---|---|---|
| `GAP-016` | Design consolidated; implementation plan pending | Free shipping needs optional campaign budget/per-order cap, authoritative shipping inputs, concurrency-safe reservations, final commit, expiry/failure recovery, and cost-based reversal. | Implement the same provider-neutral atomic coordinator port through a future distributed adapter. Budgets/caps remain optional; the client supplies actual shipping cost; the result is a full waiver or none; reservation TTL is configurable with a 15-minute default; expiry/recovery are money; and currency must match with no conversion. Event-driven reversals remain planned. See [Free-Shipping Budget Authority, Reservations, and Reversals](../superpowers/specs/2026-07-23-free-shipping-budget-authority-design.md). |
| `GAP-017` | Deferred | Event definitions exist in the demo/configuration model, but no production event-ingestion, mapping, or dispatch runtime exists. | Future runtime keeps event definition, integration mapping, and module binding separate. Events may trigger Loyalty earning, Referral qualification, Affiliate attribution/commission, analytics, or reversal adapters; event-triggered Loyalty remains explicitly future work. |
| `GAP-018` | Deferred | Loyalty has future configuration contracts but no runtime wallet/accrual ledger or configurable asset catalog. | Let merchants bind a published event to earning rules and configure terminology such as Points, Credits, Miles, Stars, or Cashback through a wallet asset catalog. |
| `GAP-019` | Deferred | Affiliate and Referral have conditional-reward configuration contracts but no production authoring/runtime, attribution, settlement, or fulfilment. | Implement module-specific runtimes against the shared typed condition/reward structures when a client requires them. |
| `GAP-020` | Deferred | Initial Admin/Operator/Viewer permissions are extensible in code, but there is no custom-role editor. | Keep permission checks action-based and deny-by-default; add stored role composition/UI when a real client needs custom roles. |
| `GAP-021` | Deferred until integration choice | Shopify and other platforms do not universally expose authoritative merchant-incurred shipping/carrier cost or historical product cost in the same payload. | Keep canonical cost facts separate. Connector mappings may use platform fields, merchant metadata, ERP/3PL enrichment, or the explicit reversal API without changing Core callsites. |
| `GAP-022` | Done | Public API failures returned a correlation ID but handled exceptions were not emitted as structured logs with that ID. | Task 7 added centralized sanitized `api_request_failed` events. Focused API tests prove the response header, error body, signed snapshot where applicable, and log share one ID, while credentials, submitted codes, request bodies, customer data, identifiers, SQL, and stacks remain absent. Staging `OBS-API-01` returned and logged matching correlation `2f6dffe6-d497-43f1-a088-f29df0a3f015`; the located event had the expected route/method/code/status and safe tenant/credential identifiers, with no sensitive request, customer, business, SQL, or stack data. |
| `GAP-024` | Deferred pending wallet runtime | The live Promo reward selector supports commerce discounts and free shipping only. A client cannot yet configure a conditional promotion that grants a Loyalty asset such as Points, Credits, Miles, Stars, or Cashback. Future Loyalty and wallet-accrual contracts exist, but they are explicitly configuration-only and have no production ledger, fulfilment runtime, or live operator routes. | Build the provider-neutral wallet/accrual ledger and fulfilment port before enabling publication. Then allow eligible program modules, including Promo when the business case is “buy/do X, receive loyalty value,” to select a configured wallet asset and emit an exact accrual effect without coupling Promo callsites to the Loyalty implementation. Merchant terminology comes from the asset catalog. |
| `GAP-027` | Approved follow-up; design specification and implementation plan pending | Operators can enter a numeric Promo priority, but a large inventory has no ranked view that makes the effective order easy to inspect or safely rearrange. | Keep explicit integer priority in create/edit. Add separate automatic and code-triggered ranked views with search/filtering and drag reordering. A reorder renumbers the affected lane atomically through an explicit review-and-publish action and must not publish unrelated Promo drafts. Rebalancing all ranked Promos in that lane is acceptable at initial scale; optimize only when measured scale requires it. |
| `GAP-028` | Approved follow-up; design specification and implementation plan pending | Operators cannot declare that particular incentives must not be applied together; the current Promo `stackable` flag cannot express pair-specific incompatibility or extend cleanly across future modules. | Define a versioned, tenant-level compatibility graph using stable `{ type, programRef }` identities. Support `exclusive` and symmetric `incompatible_pair` rules, with no rule meaning compatible. Expose and enforce Promo-to-Promo rules first, while keeping the contract extensible to Affiliate, Referral, and Loyalty. If any qualified submitted-code combination conflicts, reject the entire qualified combination, retain independent invalid/ineligible outcomes, cancel its reservations, and return `CODE_COMBINATION_NOT_ALLOWED`. |
| `GAP-029` | Open | Successful public API requests return an `x-correlation-id` and evaluations persist it, but the API emits no sanitized success/completion event containing that ID. A successful evaluation therefore cannot be reliably located in Cloudflare Logs by the response correlation ID. | Add a centralized sanitized `api_request_completed` event with correlation ID, route template, method, status, duration, and safe tenant/credential identifiers. Never log authorization values, submitted codes, request/response bodies, customer data, evaluation/order/idempotency references, SQL, or stacks. Define production sampling separately while retaining 100% staging evidence coverage. |
| `GAP-030` | Approved follow-up; design specification and implementation plan pending | Promo evaluation returns selected effects but not an authoritative checkout-price breakdown. A client cannot directly see the original merchandise subtotal, exact amount waived by each selected Promo, total discount, discounted subtotal, or line-item allocation. | Before the Evaluation Playground, extract the existing projected-discount arithmetic into one pure pricing calculator and use its exact result for evaluation output, budget/cap checks, the signed decision snapshot, redemption, and audit/reversal evidence. Return integer-minor-unit totals plus per-Promo/reward allocations; include line identity for line-item discounts. Treat this as merchandise pricing, not the final amount payable. Do not invent a monetary free-shipping saving until the authoritative shipping-cost flow in `GAP-016` exists. |
| `GAP-031` | Approved follow-up; design specification and implementation plan pending | Percentage order and line-item discounts cannot be given an optional maximum monetary discount, so a high-value basket may consume more budget than the operator intended. | Add an optional exact-currency `maximumDiscountAmount` to percentage rewards. Apply it inside the shared pricing calculator, validate it in contracts and operator authoring, and persist the capped amount in the signed evaluation/redemption evidence. Keep all arithmetic in integer minor units. |
| `GAP-032` | Deferred until a client requires the breadth | The Promo module does not match Voucherify's complete campaign breadth: bulk unique-code pools/distribution, new-price discounts, free products, BOGO/bundles, dynamic formulas, reusable catalog collections, recurring weekday/hour schedules, and richer stacking categories/policies are absent. | Do not turn the first-client platform into a speculative Voucherify clone. Preserve extension seams: many codes may later map to one stable Promo without changing `/v1/evaluate`; new reward types remain discriminated effects; catalog targeting can sit behind connector-neutral references/conditions; schedules and stacking policies remain versioned configuration. Implement each capability only when a client case justifies its contract and acceptance tests. |

## Scope decision

Gate C continues against the originally approved behavior: free shipping may be
created without a monetary budget. `GAP-001` is fixed and passed its staging
retest. The larger financial authority in `GAP-016` does not silently expand
Gate C and receives its own implementation plan, branch, verification, and
status. Shopify/manual integration remains uncommitted.
