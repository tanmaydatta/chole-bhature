# GAP-030/031 automated end-to-end verification

**Updated:** 2026-09-25
**Status:** Local three-Worker/real-D1 scenario verified; staging not deployed or executed

The [E2E workspace guide](../../tests/e2e/README.md) is the command and
cleanup runbook. To watch the operator browser flow from a fresh checkout:

```sh
pnpm install --frozen-lockfile
pnpm e2e:local:headed
```

This opens system Chrome, starts disposable Core, Identity, and Operator
Workers with private migrated Product/Auth D1 stores and unique loopback ports,
bootstraps a root through the supported local CLI and actual passkey UI, then
closes the stack. `pnpm e2e:local` runs the complete API/browser suite headlessly
with two bounded Playwright workers. No shared `.dev.vars`, `.wrangler` state,
fixed test identity, or manually created root state is needed.

## Exact fixture and assertions

The API scenario composes only the required recipes: a run-owned merchant,
published schema, customer, publishable/secret credentials, two authored and
published Promos. It reads each published operator configuration back before
evaluating. The first Promo is a 25% order discount capped at GBP 15.00,
priority 20, with GBP 50.00 budget. The second is a GBP 5.00 fixed discount
per matching item, priority 10, also with GBP 50.00 budget. Both are coded,
stackable, and scoped to one random run ID.

| Cart line | Quantity × unit price (minor units) | Fixed-Promo line allocation |
|---|---:|---:|
| Same product, line 1 | 1 × 4,001 | 500 |
| Same product, line 2 | 2 × 1,500 | 1,000 |
| Other product | 1 × 3,000 | 0 |

The original merchandise subtotal is **10,001**. The percentage would floor
to 2,500 but caps at **1,500**; the fixed Promo contributes **1,500**. The
asserted total discount is **3,000** and the discounted merchandise subtotal
is **7,001**. The scenario parses full evaluation/redemption contracts and
asserts the exact allocation order, rule IDs, line allocations, signed evidence
integrity, redemption result and ledger entries, one usage and 3,500 remaining
budget for each Promo. A byte-equivalent idempotent retry must leave result,
ledger, counters, and budget unchanged; changed reuse of the key must return
`409 VERSION_CONFLICT`.

These persistence assertions use the root- and run-proof-protected, staging-only
read-only inspection operation, not status codes or direct remote D1 writes.
The operation returns sanitized breakdown/result/ledger/counter data and HMAC
verification booleans, not secrets. The same inspection runs against real local
Workers/D1 and is wired for staging; **no staging result is claimed here**.
Tampered/stale evidence, historical envelope compatibility, atomic bundle
failure, and additional edge cases remain covered by focused Core/engine tests;
the deployed Playwright scenario does not inject tampered evidence.

The browser spec opens the actual Promo edit page, checks the cap field is
`1500`, changes it and restores it, saves, reloads, verifies the GBP 15.00
detail summary, checks operator API persistence, uses the publication dialog,
then verifies active revision 1 and the persisted published reward. It first
publishes a schema because Core requires a published schema before a Promo can
publish. This is a small user-interaction smoke; the more detailed business
assertions stay in faster API tests.

## Concurrent ownership and disposal

Every scenario has a cryptographically random `e2e_` run ID and run-scoped
merchant, user, Promo/code, customer, order, and idempotency identifiers. Two
complete scenarios run concurrently and verify distinct IDs and exact results.
Another test starts two complete local stacks simultaneously and proves their
ports, Product/Auth D1 stores, and root sessions are isolated. The bounded
two-worker default avoids unbounded bootstrap or browser cost.

Successful and intentionally failing scenarios both call `cleanup-run` in a
`finally` path. The service checks server-side run provenance and proof,
previews inventory, disposes Product then Auth in a resumable saga, and records
sanitized audit tombstones. Playwright reopens a read-only inventory and asserts
**zero run-owned Product/Auth rows** and every manifest resource marked
cleaned. The production guard fails closed; a normal local Worker has no
cleanup path. Disposal is irreversible, so never point a run at a normal
merchant. If disposal fails, use the same run's private manifest and the
documented preview/execute recovery commands; do not write remote D1 directly.

## Staging gate and evidence boundary

Staging requires a separately authorized application of any pending Product
migration `0007` followed by `0008`, Auth migrations `0005` and `0006`, and matching Core, Identity, and
Operator Workers. The global setup first checks the private root storage state
and a **read-only version/capability handshake** across all three Workers and
both D1s. Old or mixed Worker versions and missing migration markers/tables
fail before the first fixture write. The owner obtains the session with
`pnpm e2e:staging:login --output /absolute/private/root-state.json`, using the
real passkey UI. See [deployment order](../integration/staging-operations.md#e2e-platform-deployment-order)
and [copy-paste commands](../../tests/e2e/README.md). Do not execute staging
automation until the new deployment plan is separately approved.

Record command, exit code, test count, elapsed time, deployed Worker versions,
sanitized run IDs, exact expected/actual allocations and counters, and final
zero-row inventory. Never attach cookies, bearer tokens, proof values, raw HMAC
material, or sensitive customer data to evidence. The first local baseline was
5 Playwright tests in 23.9 seconds; a visible browser-only run passed in 18.1
seconds including fresh stack bootstrap. Re-measure after deployment and use
project selection or Playwright sharding only when preserving all assertions.
