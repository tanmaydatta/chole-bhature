# GAP-030/031 End-to-End Test Plan

**Updated:** 2026-09-25

**Status:** Executable local plan; staging execution requires separate owner approval

This plan verifies the authoritative merchandise price breakdown and optional
exact-currency percentage maximum from operator authoring through evaluation,
signed evidence, atomic redemption, persistence, and idempotent replay. It does
not deploy, migrate staging, or treat merchandise pricing as a final tax,
shipping, or payment total.

## Required environment

- Node and pnpm versions supported by the repository.
- Dependencies installed with `pnpm install --frozen-lockfile`.
- Cloudflare workerd/Wrangler binaries from the workspace install; no global
  Wrangler or remote Cloudflare access is required.
- A clean disposable local D1 test database. The Worker tests create isolated
  storage and run migrations automatically.
- For the optional manual browser check: the three local Workers started by
  `pnpm dev:local`, an authorized operator session, and disposable local
  merchant credentials. Never reuse normal checkout identifiers or Wrangler
  state.

## Exact pricing fixture

The automated full-flow test authors and publishes two compatible coded Promos:

1. priority 20: 25% order discount, maximum GBP 15.00;
2. priority 10: GBP 5.00 fixed discount per matching unit.

The cart uses integer minor units and two distinct lines for the same product:

| Line | Product | Quantity | Unit price | Expected line allocation |
|---|---|---:|---:|---:|
| `duplicate-line-1` | `duplicate-product` | 1 | 4,001 | 500 |
| `duplicate-line-2` | `duplicate-product` | 2 | 1,500 | 1,000 |
| `other-line` | `other-product` | 1 | 3,000 | 0 |

The original subtotal is 10,001. The uncapped 25% calculation floors to 2,500,
then the monetary maximum reduces it to 1,500. The fixed line Promo contributes
1,500. Expected `totalDiscount` is 3,000 and expected
`discountedMerchandiseSubtotal` is 7,001. These values are hand-derived; a test
failure catches cap-order, rounding, duplicate-product identity, quantity, or
stacking regressions rather than restating calculator output.

The acceptance path is the test named `carries exact capped and line allocations
from authoring through idempotent redemption` in
`apps/api/test/full-flow.test.ts`. It uses real operator services, Hono handlers,
workerd, and D1. It must prove:

- operator draft creation and publication for capped and fixed Promos;
- customer plus cart fixture setup with duplicate product IDs and distinct
  stable line identities;
- deterministic priority order and the exact basket/line allocation above;
- `price_breakdown_json` equals the public evaluation result and is covered by
  the decision HMAC;
- redemption returns the same breakdown, persists a version-3 signed result,
  writes ordered per-Promo ledger entries, increments usage once, and decrements
  each budget by exactly its own 1,500 allocation;
- an exact retry returns the byte-equivalent canonical result without a second
  ledger row or counter movement; and
- changed reuse of the idempotency key returns `409 VERSION_CONFLICT`.

## Database and API assertions

For a passing run, assert all of the following rather than relying on HTTP 200
alone:

- evaluation response parses through `EvaluationResponseSchema` and contains
  the hand-derived breakdown;
- `evaluation_decisions.price_breakdown_json` exactly matches it;
- changing signed request, decisions, diagnostics, facts, expiry, or price
  breakdown without a valid HMAC prevents commit;
- redemption response parses through `RedemptionResponseSchema` and repeats the
  same breakdown;
- `redemptions.result_json.version` is `3` and its signed result includes the
  breakdown;
- ordered `redemption_entries.discount_minor_units` values are 1,500 and 1,500;
- `program_counters.usage_count` is 1 and `budget_remaining` is 3,500 for each
  Promo after first commit and is unchanged after retry;
- no redemption header, child, counter, or operation guard is left behind when
  an atomic bundle fails.

## Manual local browser check

This supplements rather than replaces automated assertions:

1. Start the disposable local stack with `pnpm dev:local`.
2. Sign in as an authorized operator and open a new Promo draft.
3. Choose a percentage order or line discount. Add a maximum, select GBP, enter
   `1500` minor units, save, hard-refresh, and confirm the value remains.
4. Remove the maximum, save, hard-refresh, and confirm the reward is uncapped.
5. Add the GBP 15.00 maximum again, publish, and verify the Promo detail summary
   displays the cap before using it in evaluation.
6. Using disposable local credentials, submit the exact cart fixture above and
   compare every decision/allocation/total with the expected table.
7. Redeem once and retry the identical request. Confirm identical results; then
   change the order reference while reusing the key and confirm the conflict.

Capture screenshots of authoring/detail and sanitized JSON/SQL assertions. Do
not capture bearer tokens, submitted business codes, customer data, or raw HMAC
material.

## Optional staging check

Staging is not part of this implementation turn. If separately approved, use
the protected staging procedure and a fresh disposable merchant/Promo/customer,
apply migration `0007`, deploy the matching API and Operator Web revisions, and
repeat the manual case. Add tampered evidence only through an approved isolated
test hook; never edit shared staging rows ad hoc. Record Worker version IDs,
migration status, safe evaluation/redemption identifiers, exact expected versus
actual allocations, counter totals, and correlation IDs. A staging check fails
if any component is on a mixed contract version.

## Teardown and pass/fail evidence

Automated workerd storage is disposable and ends with the test process. For a
manual local run, stop `pnpm dev:local` and remove only the documented disposable
local Worker/D1 state after confirming it is not shared. Delete or end only the
fixtures created for this plan.

Pass evidence consists of the exact command, exit code 0, test counts, date,
current commit/diff identity, and any warnings. Fail the plan on any unexpected
response field, allocation/order/rounding difference, HMAC acceptance after
tampering, duplicate counter movement, partial database write, missing UI cap,
or command warning that indicates a correctness issue. Do not mark staging
verified from local evidence.
