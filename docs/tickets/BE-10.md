# BE-10 · POST /v1/evaluate
> **Phase 0 (M0):** Phase 0 (**P0-6**) delivers promo-only `evaluate` reading config from D1. Remaining Phase 1 scope: KV hot-read, wallet-balance read, referral-priority selection, and the other program types.

> ⚠️ Detailed from the spec — refresh from the outputs of its dependencies before starting (see "Depends on").

## Context
Spec §4 (evaluate contract), §6 (engine), §3.2 (evaluate is stateless/read-only; reads never touch the counter DO). Depends on BE-3, BE-6, BE-8, BE-9.

## Scope
- `POST /v1/evaluate`: accepts `customerRef` + attributes, cart/context variables (`basket_value`, `items_in_basket`, `category`, …), an optional entered `code`; publishable key allowed.
- Pipeline: read `CONFIG_KV["config:{merchantId}"]` (BE-6) → run BE-3's condition evaluator against merged user/dynamic/system variables → resolve an entered code against `codes` → apply stacking rules → interpolate messages (`renderMessage`) → check `exhausted` KV flags (BE-8) for fast-fail on capped programs → read wallet available balance (BE-9).
- Response: applicable discounts/rewards per program (respecting stacking; loyalty never stacks), available wallet credit, resolved/interpolated messages.

## Acceptance criteria
- [ ] Returns correct discounts/rewards for at least one scenario per program type (promo, affiliate via code, referral, loyalty wallet).
- [ ] Never calls `ProgramCountersDO` directly — only reads the KV `exhausted` flag for capped programs (Spec §3.2: reads never touch the counter).
- [ ] The first-failing condition drives the returned message via the fallback chain (per-condition → per-variable default → program fallback → system default).
- [ ] Stacking is respected per program flags; a loyalty reward never stacks with another reward.
- [ ] A publishable key is sufficient to call this endpoint (BE-2 key-kind gating).
- [ ] A correctness test suite covers each program type (concurrency is QA-1's job, not this ticket's); tests green.

## Technical notes
- Edge-fast by design (Spec §3.2) — no D1 read on the hot path; everything comes from `CONFIG_KV` plus two cheap DO reads (wallet balance, exhausted flag).
- Uses BE-3's evaluator, `renderMessage`, and `rewardSummaryFor` directly — no re-implementation of condition logic here.
- This is a read; Spec §3.2 explicitly notes the UX race (a shown discount can be lost before checkout) — `redemptions` (BE-11) is the authoritative moment, not this endpoint.

## Interfaces
**Consumes:** BE-3 evaluator/`renderMessage`/`rewardSummaryFor`/types; BE-6 `CONFIG_KV["config:{merchantId}"]` contract; BE-8 `exhausted:{merchantId}:{programId}` KV flag; BE-9 wallet live-balance read.
**Produces:** the `POST /v1/evaluate` request/response contract (discounts/rewards array + wallet available credit + resolved messages) — consumed by BE-15 (referral priority selection extends this pipeline), FE-6 (reference storefront), DOCS-1 (API reference).

## Out of scope
- Any write/decrement (BE-11 owns redemption-time mutation).
- Reserve-then-commit holds (post-MVP, Spec §3.2).
