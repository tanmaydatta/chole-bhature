# BE-15 · Referral priority + fulfillment

> ⚠️ Detailed from the spec — refresh from the outputs of its dependencies before starting (see "Depends on").

## Context
Spec §7 — referral behavior: "attribute-based priority selection... engine picks the first matching program; customer never chooses." Depends on BE-10 (evaluate) and BE-12 (events).

## Scope
- Priority-selection logic added to BE-10's evaluate pipeline: when multiple referral programs could match a customer, pick the first match by defined priority order — never a customer-facing choice.
- Referrer wallet credit hooked into BE-12's event consumer: on the referee's qualifying event, credit the referrer's `CustomerWalletDO`.

## Acceptance criteria
- [ ] Given multiple matching referral programs for a customer, evaluate returns exactly one (the first by priority).
- [ ] A referee's qualifying event (per `event_defs`) triggers exactly one referrer wallet credit, idempotent by event id (reusing BE-12's dedupe).
- [ ] The referee-side reward (surfaced in evaluate) and the referrer-side credit (from the event) use the same priority selection — no mismatch between who evaluate says referred whom and who gets credited.
- [ ] Tests green covering priority ordering and referrer-credit-on-event.

## Technical notes
- This ticket doesn't introduce new endpoints — it extends BE-10's evaluate and BE-12's consumer with referral-specific selection/credit logic.
- Referral codes reuse BE-14's `codes` table shape (Spec §7: "code/link").

## Interfaces
**Consumes:** BE-10 evaluate pipeline (extension point for priority selection); BE-12 event consumer + wallet-credit RPC path.
**Produces:** the referral priority-selection rule and the referrer-credit-on-event flow — consumed by FE-6 (reference storefront demonstrates the full referral loop), DOCS-1/DOCS-2 (referral behavior documentation).

## Out of scope
- Affiliate code generation (BE-14, a separate program type).
- Multi-touch/last-click attribution models beyond "first matching program" (not in Spec §7).
