# BE-11 · POST /v1/redemptions

> ⚠️ Detailed from the spec — refresh from the outputs of its dependencies before starting (see "Depends on").

## Context
Spec §4 (redemptions contract, idempotent by order id) and §3.2 (DO is the single arbiter; redeem-before-capture rule). Depends on BE-8 (counters) and BE-14 (codes).

## Scope
- `POST /v1/redemptions`: order id, applied program(s)/code(s), amounts, `customerRef`; secret key only.
- Idempotent by order id — a repeated call with the same order id returns the original stable result; no double-decrement.
- Effects: atomic decrement + cap check via `ProgramCountersDO` (BE-8); append a row to `redemptions` (D1 ledger, BE-1) including per-code attribution (BE-14's codes).

## Acceptance criteria
- [ ] The first call for a new order id decrements the correct program's DO and inserts one `redemptions` row.
- [ ] A retried call with the same order id is a no-op returning the same result (no second decrement, no duplicate row).
- [ ] A redemption against an exhausted program is rejected, matching the Spec §3.2 "checkout re-prices" contract merchants integrate against.
- [ ] Per-code redemptions record which code was used, for BE-14's per-code stats.
- [ ] Secret-key only (publishable key rejected).
- [ ] Covered by QA-1's concurrency suite; non-concurrent correctness cases green here.

## Technical notes
- This is the authoritative moment merchants MUST call before capturing payment (Spec §3.2 integration rule) — this ticket's job is correctness/idempotency; enforcing call order is the merchant integration's responsibility, demonstrated in FE-6.
- Idempotency dedupe-key storage lives alongside the DO/dedicated store per Spec §5.

## Interfaces
**Consumes:** BE-8 `ProgramCountersDO` decrement/cap-check RPC; BE-14 `codes` table/attribution model; BE-1 `redemptions` table.
**Produces:** the `POST /v1/redemptions` idempotent contract and the `redemptions` ledger write — consumed by BE-15 (referral fulfillment trigger point), BE-17 (rollups), BE-18 (reliability-pass target), FE-6 (checkout flow), QA-1/QA-2/QA-3 (test targets), DOCS-1.

## Out of scope
- Wallet crediting from events (BE-12).
- Reserve-then-commit holds (post-MVP).
