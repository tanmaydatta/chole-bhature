# P0-7 · Dashboard: api-client (token auth, no login) + promo CRUD screens

## Context
Phase 0 ticket (M0 · Client Demo) — the single-engineer, promo-only slice. Delivers capability 3's surface (Spec §1): the client does CRUD on promos via the dashboard against the live API. Spec §3 keeps `apps/dashboard` as the ported `demo/`; this ticket swaps its in-memory data layer for the real API with no redesign. Depends on P0-5.

## Scope
- `apps/dashboard/src/lib/api-client.ts` — a typed fetch wrapper (base URL, sends the secret token; NO session login).
- Wire the promo list / detail / create / edit screens + the condition builder to `/v1/programs` via the client, replacing the in-memory `data/store.ts`.
- Keep the demo UI and flows unchanged — this is a data-layer swap, not a redesign.

## Acceptance criteria
- [ ] A promo can be created / edited / viewed / deleted end-to-end against the live API (no mock-store fallback).
- [ ] The condition builder round-trips a `ConditionGroup`, including one nested level.
- [ ] The existing demo tests for these screens pass against the client with the network boundary mocked.
- [ ] Tests green.

## Technical notes
- The secret token is sent by the client (Spec §4 honest limitation: it ships in the dashboard bundle in Phase 0). No session login.
- Types come from `packages/engine` (P0-3) so the client and screens share the promo/config/`ConditionGroup` shapes with the API.
- The wiring pattern established here (typed client → real API) is the pattern Phase 1 reuses for the remaining screens.

## Interfaces
**Consumes:** P0-5's `/v1/programs` contract + P0-3's engine types.
**Produces:** the `api-client` + real-data promo CRUD screens (the wiring pattern Phase 1 reuses).
Seeds Phase 1 **FE-1** (Phase 1 adds session-auth login + a route guard in front of the client) and **FE-2** (Phase 1 adds the other 3 program types to the screens).

## Out of scope
- Login / signup / auth guard.
- The other program types.
- Variables / events / api-keys / billing screens.
