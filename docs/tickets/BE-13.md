# BE-13 · Customers upsert + wallet endpoints

> ⚠️ Detailed from the spec — refresh from the outputs of its dependencies before starting (see "Depends on").

## Context
Spec §4 (customers upsert + wallet read endpoints). Depends on BE-9 (wallet DO).

## Scope
- `POST /v1/customers` upsert: `customerRef` + user attributes (for user-attribute conditions, wallet identity, referral identity); secret key.
- `GET /v1/customers/{ref}/wallet`: balance + recent transactions; publishable (read) or secret.

## Acceptance criteria
- [ ] Upsert creates a new customer or updates attributes on an existing one, scoped by `merchant_id`.
- [ ] The wallet endpoint returns the DO's live balance (not a stale D1-derived sum) plus recent `wallet_transactions` rows.
- [ ] The wallet endpoint is callable with a publishable key (read-only) per Spec §4.
- [ ] Tests green.

## Technical notes
- Balance comes from `CustomerWalletDO` (BE-9); recent transactions come from D1 `wallet_transactions` (BE-1) — this endpoint reads both and merges, per the Spec §3 data-ownership rule.
- User attributes passed directly in `/v1/evaluate` requests (Spec §4) are independent of this upsert — this ticket persists the customer record, it does not feed evaluate's per-request attribute input.

## Interfaces
**Consumes:** BE-9 `CustomerWalletDO` live-balance read; BE-1 `customers`/`wallet_transactions` tables.
**Produces:** the `POST /v1/customers` and `GET /v1/customers/{ref}/wallet` endpoints — consumed by FE-6 (wallet display + customer upsert on checkout), DOCS-1 (API reference).

## Out of scope
- Attribute-based condition evaluation itself (BE-10 receives attributes directly in the evaluate request per Spec §4; this ticket only persists them for the customer record).
- Wallet credit/debit mutations (BE-9 owns those RPCs; this ticket only reads).
