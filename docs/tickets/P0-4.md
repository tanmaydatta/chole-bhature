# P0-4 · Hono API skeleton + static-token gate (publishable/secret), single-tenant

## Context
Phase 0 ticket (M0 · Client Demo) — the single-engineer, promo-only slice. Spec §4 defines the single-merchant lockdown: a Hono middleware validates a **static token** on every request and resolves it to the single hardcoded merchant (401 otherwise), with two token kinds mirroring Phase 1's publishable/secret split. This is an access gate, not a hardened secrecy boundary — Phase 1 replaces it via the same seam. Depends on P0-1's `apps/api`.

## Scope
- A Hono app in `apps/api`.
- Middleware validating a static token per request and resolving it to the single hardcoded merchant (401 otherwise).
- Two token kinds read from Workers secrets: SECRET (guards writes — program CRUD + `POST /v1/redemptions`) and PUBLISHABLE (guards reads — `GET /v1/promos` + `POST /v1/evaluate`).
- zod validation middleware with a consistent error shape.
- A "current merchant" resolver stub that Phase 1 replaces with real auth.

## Acceptance criteria
- [ ] A request without a valid token → 401.
- [ ] A secret-only route rejects a publishable token, and a publishable-only route rejects a secret token.
- [ ] The merchant resolver returns the single hardcoded merchant.
- [ ] A health route responds.
- [ ] Tests green.

## Technical notes
- Both tokens are read from Workers secrets (Spec §4). Honest limitation: the publishable token, and in this demo the dashboard's secret token, ship in client bundles — this is an access gate, not a secrecy boundary.
- The "current merchant" resolver is a stub occupying the exact seam Phase 1's real auth plugs into — the middleware shape and publishable/secret split stay stable, so Phase 1's swap is drop-in.

## Interfaces
**Consumes:** P0-1's `apps/api` (Hono + wrangler).
**Produces:** the Hono app + static-token-gate middleware + current-merchant resolver + zod validation middleware/error shape — consumed by P0-5 (program CRUD + `GET /v1/promos`) and P0-6 (`POST /v1/evaluate` + `POST /v1/redemptions`).
Seeds Phase 1 **BE-2** (Phase 1 swaps the static tokens for hashed, rotatable, D1-backed API keys + rate limiting, through the same middleware seam and publishable/secret split).

## Out of scope
- Rate limiting, API-key management, session login (Phase 1 BE-2/BE-4/BE-5).
