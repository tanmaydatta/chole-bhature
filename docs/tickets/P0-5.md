# P0-5 · Promo CRUD API + GET /v1/promos

## Context
Phase 0 ticket (M0 · Client Demo) — the single-engineer, promo-only slice. Delivers capability 3 (client CRUD on promos) and capability 1's read surface (Spec §1). Spec §5 pins `GET /v1/promos` → publicly-listable active promos, gated by a `listed` flag so secret-code promos don't leak. Depends on P0-2 (schema), P0-3 (engine zod), P0-4 (middleware).

## Scope
- `/v1/programs` CRUD (POST/GET/PATCH/DELETE) for the promo type, secret-token gated; config validated by the engine's zod schema (P0-3).
- `GET /v1/promos` (publishable-token gated) returning active promos with `listed = true` — name, description, reward summary, and a code-required flag.

## Acceptance criteria
- [ ] Create/read/update/delete a promo persists in D1.
- [ ] The `listed` flag hides secret-code promos from `GET /v1/promos`.
- [ ] An invalid config is rejected by the engine's zod schema.
- [ ] The correct token kind is enforced per route (secret for `/v1/programs`, publishable for `/v1/promos`).
- [ ] Tests green.

## Technical notes
- Config JSON is validated against P0-3's zod schema before persisting to `programs.config`; D1 does not validate it.
- `GET /v1/promos` derives the reward summary via the engine's `rewardSummaryFor` and reports whether a code is required — the same contract Phase 1 serves.

## Interfaces
**Consumes:** P0-2's `programs` table + `db` factory, P0-3's zod/types + `rewardSummaryFor`, P0-4's token-gate + validation middleware.
**Produces:** the `/v1/programs` CRUD contract + the `GET /v1/promos` list contract — consumed by P0-6 (reads promo config), P0-7 (dashboard CRUD screens), and P0-8 (storefront offers list).
Seeds Phase 1 **BE-6** (Phase 1 adds variables/events CRUD + a KV compiled-config cache in front of the D1 reads).

## Out of scope
- Variables/events endpoints.
- KV compiled-config cache (Phase 1).
