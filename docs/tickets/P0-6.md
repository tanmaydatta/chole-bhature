# P0-6 · POST /v1/evaluate + POST /v1/redemptions (promo-only, atomic caps, idempotent)

## Context
Phase 0 ticket (M0 · Client Demo) — the single-engineer, promo-only slice. Delivers capability 2 (price it → commit it) from Spec §1. Spec §6 pins the correctness mechanism: because D1 is SQLite and writes are serialized, a single conditional `UPDATE` is atomic and cannot oversell — no Durable Object needed in Phase 0. Idempotency is D1-native via the unique `(merchant_id, order_id)` on `redemptions`. Depends on P0-5.

## Scope
- `POST /v1/evaluate` (publishable) — inputs `{ customerRef?, cartContext, code? }`; reads promo config from D1; runs the engine evaluator over merged user/dynamic/system variables; resolves an entered code; interpolates the message via `renderMessage`; returns discount + message. Read-only.
- `POST /v1/redemptions` (secret) — inputs `{ orderId, programId | code, amounts }`; idempotent by `(merchant_id, order_id)`; an ATOMIC conditional `UPDATE` guards the budget/usage cap (reject when `rowsAffected == 0`); the counter `UPDATE` + ledger `INSERT` run together in one `batch()`.

## Acceptance criteria
- [ ] `evaluate` returns the correct promo discount and the first-failing-condition message (the fallback chain).
- [ ] The first `redemptions` call for an `orderId` decrements the counter and inserts one ledger row.
- [ ] A retried `orderId` is a no-op that returns the same result — no double decrement, no second ledger row.
- [ ] A capped promo rejects once exhausted.
- [ ] The correct token kind is enforced per route (publishable for `evaluate`, secret for `redemptions`).
- [ ] Non-concurrent correctness tests green.

## Technical notes
- The atomic conditional-`UPDATE` from Spec §6:
  ```sql
  UPDATE programs
     SET usage_count = usage_count + 1
   WHERE id = ?1 AND merchant_id = ?2
     AND (budget_remaining IS NULL OR budget_remaining >= ?3)   -- discount amount
     AND (max_uses        IS NULL OR usage_count < max_uses)
  ```
  If `rowsAffected == 0` → promo exhausted → reject (checkout re-prices). The counter `UPDATE` + ledger `INSERT` run in one Drizzle `batch()` so they commit together.
- `ProgramCountersDO` is **deferred** (Phase 1 / BE-8 SCALE upgrade — edge-fast counters, ~1k+ ops/sec, the flash-sale scenario), **not** the correctness mechanism. The endpoint contract is unchanged, so Phase 1 swaps only the internals.

## Interfaces
**Consumes:** P0-5's promo config (`/v1/programs`), P0-3's engine evaluator + `renderMessage`, P0-2's `programs` + `redemptions` tables + `batch()`.
**Produces:** the `POST /v1/evaluate` + `POST /v1/redemptions` contracts — consumed by P0-8 (storefront checkout).
Seeds Phase 1 **BE-10** (Phase 1 adds KV hot-read, wallet read, and referral priority to `evaluate`) and **BE-11** (Phase 1 swaps the D1 conditional-update for `ProgramCountersDO` behind the unchanged `redemptions` contract).
